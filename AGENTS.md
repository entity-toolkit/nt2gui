# Description
- This is a scientific visualization app which has two components: a backend server, and a frontend UI 
- The backend is written in Python with Flask and handles the data analysis and post-processing, and UI persistency.
- Packaging: one Python package, `nt2gui` (`pyproject.toml`, hatchling). `npm run build` writes the client to `nt2gui/static/` (gitignored, bundled into the wheel; the build hook refuses to build without it) and Flask serves it at `/`; the JSON API lives under `/api` (all endpoints below are relative to it). `nt2gui serve` (`nt2gui/cli.py`) runs it with waitress in a single multi-threaded process — open simulations, caches and the session are in-memory, so never use multiple worker processes, and guard shared mutable state with locks. It binds `127.0.0.1` by default and prints an SSH tunnel command; the intended setup is the server on a cluster next to the data and the browser on the user's machine. `nt2gui server` runs the API alone (`create_app(with_client=False)`) and `nt2gui client` the UI alone (`nt2gui/static_client.py`, no data dependencies); a separately served UI calls the API cross-origin, which is allowed only for `--allow-origin` origins (CORS allowlist in `app.py`, default the client's `http://localhost:8766`) because the API can write files on the server.
- The client uses relative URLs by default (`client/src/config.ts`, vite `base: "./"`) so it works behind any port or path prefix; `npm run dev` proxies `/api` to Flask. A different server URL can be set per browser (Settings, the offline screen, or a `?server=` link); it is stored in localStorage, not in the synced session. `npm run package` builds the client and then the wheel/sdist; CI (`.github/workflows/ci.yml`) tests, builds, and publishes to PyPI on `v*` tags.
- Ultimately, the backend will be paired with the `nt2py` package to provide a UI for visualization (https://github.com/entity-toolkit/nt2py)
- The frontend is a react-based vite app written in typescript which uses flex-layout for to display multiple panels with selectable plots.
- The UI state should be synchronized with the server which must keep track of it and potentially recover at initialization.
  - The server owns the session (`nt2gui/session/store.py`): it always has a valid state (defaults from `nt2gui/session/schema.py`), persists it to `$NT2GUI_STATE_FILE` (default `.nt2gui/session.json`) with atomic writes, and re-opens saved simulations on restart.
  - `GET /state` returns `{revision, state, simulations}`; `PUT /state` takes `{revision, state}` and returns 409 with the current snapshot when the revision is stale. Simulation commands return the same snapshot.
  - Saved sessions (`nt2gui/session/files.py`, which also holds the schema migrations) are the session without its revision: `{schemaVersion, state, simulations}`. `POST /session/save|load {path}` writes/reads files on the server machine (409 on overwrite unless `overwrite: true`); `GET /session/export` and `POST /session/import {session}` back the client-side download/upload. Loading replaces the whole session, re-opens its simulations (reporting failures in `warnings`), and bumps the revision.
  - The client never initializes the state: it renders only after `GET /state`, and all writes go through `client/src/state/StateSync.ts` (debounced, serialized, retried; server wins on conflict).
  - When changing the state shape, update `client/src/state/schema.ts` and `nt2gui/session/schema.py` together (bump `SCHEMA_VERSION` and add a migration for breaking changes).
- Plots are shaded on the server side, but the axes as well as the colorbars (if applicable) are reconstructed on the client-side using d3 elements.
  - The server returns only the image (`nt2gui/render.py:shade`, no matplotlib figures — pyplot isn't thread-safe), its extent in data units (outer cell/bin edges) and the color limits; `client/src/charts/ImageChart.tsx` draws both 2D plot types with matching d3 scales.

# Code layout
- Server (`nt2gui/`), one direction of dependencies: `api/` → `plots/` → `data/` + `render.py` → `sources/` + `session/`.
  - `app.py` wires the `Workspace` (`workspace.py`: session store + open simulations + lock, Flask-free), the `api/` blueprints (`state`, `simulations`, `fields`, `particles`; helpers in `api/common.py`) and the static client.
  - Errors: domain code raises `nt2gui/errors.py:UserError` (or `NotFound`/`Conflict`, or subclasses like `ExpressionError`, `QuantityError`) for bad input; one handler turns them into JSON errors with their status. Routes don't try/except; anything else is a bug and a 500. Validate request bodies with the pydantic models (`api.common.parse`).
  - `plots/<kind>.py` turns a validated config into a response; `data/` holds reusable pieces (`quantities.py`: resolving quantities, `snapshot_at`, `cut`; `particles.py`: particle datasets, scales, binning; `metadata.py`; `expressions.py`).
  - Tests share fixtures in `tests/conftest.py` and helpers (`put_state`, `load_demo`) in `tests/helpers.py`.
- Client (`client/src/`):
  - `api/` (one module per server area; `http.ts` has `requestJson`, URL helpers, `serverErrorMessage`; response types in `api/types.ts`), `state/` (`schema.ts`, pure `plotters.ts` reducers, `useServerSession.ts`, `UiContext.tsx` providing `useUi()` / `useUiActions()` — no prop drilling), `charts/` (d3 charts and scales), `components/common` + `components/layout`, `lib/` (pure helpers; icons come from `react-icons/tb` (Tabler), with a `title` tooltip and `aria-label` on icon-only buttons), `hooks/` (`useCachedResource` for load-once data, `useServerRender` for latest-request-wins renders).
  - Plot kinds live in `plots/<kind>/` (Plot component using `PlotFrame`, Figure, Controls, pure `config.ts` with tests) and are listed in `plots/registry.ts`. Adding a plot type: a new folder, its config in both schemas, and one registry entry (plus a `nt2gui/plots/` module and route if it needs new data).
  - Focus mode (`state.focusMode`, `components/layout/FocusToggle.tsx` next to the sync status) hides every control: elements marked `data-ui-chrome` (menubar, sidebar, plot toolbars, time bars, slice sliders, figure notes, timeline) and the flexlayout tab bars, via `.focus-mode` in `styles/layout.css`; they stay mounted so playback continues. A faint floating toggle brings them back.
  - A new panel shows `plots/PlotPicker.tsx`: the data type (fields/particles) and, below it, that type's plot kinds from the registry (label, description, icon; `unavailable` disables a kind with a reason, e.g. 2D pseudocolor when the panel's simulation has only 1D fields). The chosen data type stays visible (dimmed) to switch it or, clicked again, go back.

# Data format on the backend
- Simulations are opened by `nt2gui/sources/__init__.py:open_simulation`: a path like `demo:run` gives synthetic data (`nt2gui/sources/demo.py`); anything else is an Entity output directory read with nt2py (`nt2gui/sources/nt2.py`, lazy dask-backed fields; particles loaded column by column). Both implement `SimulationSource` (fields, species, timeline, `particles(time, columns)`, `particle_columns`, `species_counts(time)`, particle_time(time)).
  - nt2py fields are lazy but *not cached*: every `.values` re-runs the read of a whole step (one dask chunk per step). `Nt2Simulation` therefore passes nt2py a `FieldCachingReader` that keeps each (field, step) array in a byte-budgeted `sources/cache.py:StepCache` (`NT2GUI_FIELD_CACHE_MB`). Particle columns are cached per (step, column) (`NT2GUI_PARTICLE_CACHE_MB`) and plots load only the columns their quantities need (`data/particles.py:required_columns`); metadata, summaries and expression checks read no particle data. Never add a code path that re-reads data per request. Responses are sized for the screen, not the data: 1D cuts are min/max-decimated to ≤ ~3000 points (`plots/line.py:MAX_LINE_POINTS`, `data/arrays.py:minmax_indices`; zooming re-requests the narrower range at higher detail), 2D field images average blocks of cells down to ≤ 4096 pixels per axis after the zoom crop (`plots/pseudocolor.py:MAX_IMAGE_SIZE`, `data/arrays.py:block_mean`; the response's `sampling` gives the block size, so zooming in recovers full resolution), coordinate lists in metadata are capped at ~2000 values, and JSON floats are rounded to 7 significant digits.
  - The client debounces renders and aborts superseded ones (`hooks/useServerRender.ts`, which also counts pending renders in `state/renderActivity.ts`); the server logs API requests slower than 0.5 s. Playback (`components/common/TimeControls.tsx`, used by the global `components/layout/TimelineBar.tsx` and by panels; `lib/playback.ts`) steps to the next output only once no render it drives is pending, at most at the chosen fps; the `<`/`>` keys (also `,`/`.`; ignored while typing in a field) step the global timeline one output (`steppedTime`, `TimeControls` `keyboard`) and, held, repeat the same way after `HOLD_DELAY_MS` (the key's own auto-repeat is ignored) (saved in the session: `playbackFps`, per panel `localPlaybackFps`). Renders are tracked per panel (`RenderScope`, provided by `plots/Panel.tsx`), so the global timeline waits only for panels with "Sync time" on, and an unsynced panel (`syncTime: false`, toggled at the right end of the plot toolbar; its own `localTime` on the global grid, with a timeline below the plot) waits only for itself. Zoomed plots can be dragged to pan (`charts/scales.ts:panScale`, clamped to the data's coordinate range); the drag translates the current image/lines, and after release the chart keeps the panned axes (drawing the old image/lines at their true position) until the new render arrives. nt2py knows species only by index, so labels and masses come from Entity's `<name>.info`.
- Loaded simulations have a display `name` (in the session's `simulations` records): by default the run's own (`<name>.info`, else the directory; demo: the part after `demo:`), made unique with `-01`, `-02`, … (`workspace.py:unique_name`); `PATCH /simulations/<id> {name}` renames (409 if another has it). Sessions saved without names get them on load. Panels show their simulation's name at the top only when several are loaded.
- `POST /simulations/<id>/reload` re-opens a simulation from disk (same id and name; new outputs; its timeline becomes the global one, keeping the current time where it fits). The client then calls `state/simulationData.ts:markSimulationReloaded`, which drops that simulation's entries from every `cachedLoader` (keys are the id, or the id + NUL + more) and bumps its data version (`useSimulationVersion`), which metadata hooks pass to `useCachedResource` and plot figures put in their render keys.
- `GET /simulations/<id>/attrs` returns the run's parameters (`SimulationSource.attrs`: nt2py's `Data.attrs`, flat TOML-like keys `<block>.<subblock>.<name>`) as plain JSON (`data/metadata.py:attribute_value`: bytes → text, numpy → numbers/lists); the card's "Attributes" modal (`components/layout/AttributesModal.tsx`) nests them into collapsible blocks with a filter (`lib/attributes.ts`).
- Templates (`nt2gui/session/templates.py`) are a session's panels without what ties them to one run: the layout and each plotter minus its simulation, times, zooms, slices, region filters and sync toggles (`template_plotter`; value limits are kept). They live in `templates.json` next to the session file (`config.templates_file`), independent of the session. API: `GET /templates`, `POST /templates {name, overwrite?}` (saves the server's current panels; the client flushes first; 409 if taken), `PATCH /templates/<name> {name}`, `DELETE /templates/<name>`, `POST /templates/<name>/apply {simulationId}` (replaces every panel, points them at that simulation and resets zoom; regions and timeline stay; returns the snapshot). UI: the sidebar's "Templates" dropdown (`components/layout/TemplateMenu.tsx`, `hooks/useTemplates.ts`).
- `GET /simulations/<id>/summary` (`nt2gui/data/metadata.py`) describes a simulation's fields, particles (species, masses, counts) and spectra — axes, resolution, output times, quantities — for the left sidebar where simulations are loaded.
- Integration tests in `tests/test_nt2loader.py` run against real output at `$NT2GUI_TEST_DATA` (default `~/Codes/entity/temp/deposit/dep-esirkepov`) and skip when it's absent.
- The data will consist of two different types: fields (multi-D arrays with 1D/2D or 3D coordinates at different timesteps represented with an xarray dataset), and particles (pandas dataframe containing particle species index, coordinates, ids, velocities, and corresponding timesteps etc.).
- Particle plots (`nt2gui/data/particles.py`, `nt2gui/plots/particle_*.py`) are weighted histograms of one time step: 1D (`particleHistogramConfig`, several lines of different species sharing one binned x axis) and 2D phase space (`particlePhaseConfig`, shaded on the server). Quantities are the columns (`x`, `y`, `z`, `ux`, `uy`, `uz`, `w`), `gamma = sqrt(1 + u²)`, `energy = |u|` (massless species), or expressions. Axes bin uniformly in linear, log10, or `sign(A)|A|^p` space; the client uses the matching d3 scale (`scaleLog`, sign-preserving `scalePow`) so ticks show data values. Field plots offer the same three scales for values (`components/common/ScaleSelect.tsx`): the 1D plot's y axis (`lineConfig.yScale`/`yPower`, display only) and the 2D pseudocolor colors (`pseudocolorConfig.colorScale`/`colorPower`, shaded with `render.py:sign_power`; the colorbar returns `power`). An empty species list means all species. Saved regions (`state.regions`: `region-01`, … — per-coordinate ranges and/or a lasso polygon over two spatial coordinates) are drawn with the toolbar's "Select region" tool on any plot with a spatial axis (`x y z r th ph`, shared by field coordinates and particle columns; `client/src/state/regions.ts`): a range in 1D, lasso or box in 2D, a band when only one axis is spatial. Regions can be renamed or deleted in the sidebar (`withRenamedRegion`/`withoutRegion` update every particle plot's references). Plots outline regions in per-region colors (stored on the region when saved, from its number, so renaming keeps it; `regionColor`) behind a per-plot `showRegions` toggle (default on in 1D, off in 2D). Particle plots filter by them (phase plot: `regions`; histogram: per-series `regions`; union, empty = no filter); the client sends the referenced region definitions with each render request (`nt2gui/data/regions.py` tests membership).
- Fields have names and the user should be able to combine them (and, potentially, the coordinates) to create new variables.
  - Custom quantities are expression strings (e.g. `sqrt(Ex**2 + Ey**2)`) evaluated by `nt2gui/data/expressions.py`, an AST whitelist over fields, coordinates and numpy functions — never `eval`. Anywhere a field name is accepted (1D `quantities`, 2D `field`), an expression is too; each plot keeps its list in `expressions`, and `POST /simulations/<id>/quantities/check` validates one and returns its dims.
  - Named variables (`state.fieldVariables` / `state.particleVariables`: `{name, expression}`) are shared by every plot of their kind and usable by name in plots and in other variables (`epar = edotb / sqrt(...)`). Typing `name = expression` in a custom-quantity box defines (or redefines) one; a plot's own expression can be named (`withNamedExpression`), and renaming rewrites every use (`state/variables.ts`, `hooks/useVariables.ts`). Like regions, the client sends the variables a request uses (`usedVariables`, transitive) as `variables: {name: expression}` with every render and check; the evaluator resolves them lazily, once each, reporting loops (`expressions.py`); data names win over variables. Templates carry the variables and merge them in when applied.
- Coordinate transforms (`state.coordinateTransforms`: coordinate → expression, for `x y z r th ph` and time `t`; session-wide), e.g. `(x - grid.extent[0]) / setup.skin`, `x - 0.5*t`, `t * setup.omega`. An expression may use its own coordinate, the original `t`, numpy functions and the run's attributes by dotted name (`grid.extent[0]`; `expressions.py` resolves them only where `attrs` are given). A transform doesn't replace its coordinate: it adds a primed one (`xp`, shown x′ via `state/transforms.ts:coordinateLabel`; `PRIMED`/`base_of` on the server), so plots can use either. `nt2gui/data/transforms.py:Frame` applies them per request (sent as `transforms` and `timeAxis`, like variables): `snapshot_at` adds `xp` coordinates along `x` (and a scalar `tp`), `on_axes` swaps a primed axis in for its dimension (sorted) in line/pseudocolor plots, `particles_at` adds `xp` columns (`required_columns(derived=frame.spatial)` loads `x` for them), and field metadata (`GET /fields?transforms=&timeAxis=&time=`) adds the primed coordinates (time matters only for a moving frame; `metadataFrame`). Axis menus offer x and x′ (`withPrimed`: `lineAxes`, `fieldDims`, `particleQuantities`; two plot axes can't share a dimension); regions, expressions, zooms and smoothing windows use whichever name the plot uses (`SPATIAL_COORDINATES` includes the primed names). The timeline runs in `t` or `tp` (`state.timeAxis`, the t / t′ switch on `TimelineBar`; t′ only while `t` is transformed); request and response times are on that axis and the nearest output is found among its times. `hooks/useTransforms.ts` changes transforms or the axis, refetching the timeline when its values move (`timelineMoves`; `POST /simulations/<id>/timeline` with the previous transforms/axis/time, staying at the same output) and resetting zooms when a spatial transform changes (`withTransforms`). Loading/reloading uses the session's transforms and axis for the timeline (falling back to the run's own times if they don't apply). The sidebar's "Coordinates" editor (`components/layout/TransformEditor.tsx`) offers only coordinates some loaded simulation has (`usePresentCoordinates`, from the summaries) and checks edits against every loaded simulation (`POST /simulations/<id>/transforms/check`).
- Field plots can be smoothed with a boxcar whose width is given per coordinate in coordinate units (`lineConfig.smoothing` along the plotted axis, `pseudocolorConfig.smoothing` along x/y; `data/smoothing.py`, `data/arrays.py:boxcar`, NaN-aware, O(n)). It is applied before the zoom crop (2D: on the zoom window plus a window's margin) and before downsampling, so zoomed views match the full one; responses report the width used in cells (`smoothing`).

# Guidelines
- Use both react typescript and Python best-practices.
- Run `pip install -r requirements.txt` (or `pip install -e ".[dev]"`) to install python requirements and use `npm i` to install node requirements.
- use `npm run dev` to run both the server and the client concurrently.
- The state of UI must be fully reproducible and synchronized with the server.
- Run tests with `npm run test` (typecheck + vitest + pytest), in the most error-prone routines -- always add unit tests.
