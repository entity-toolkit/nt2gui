# Description
- This is a scientific visualization app which has two components: a backend server, and a frontend UI 
- The backend is written in Python with Flask and handles the data analysis and post-processing, and UI persistency.
- Packaging: one Python package, `nt2gui` (`pyproject.toml`, hatchling). `npm run build` writes the client to `nt2gui/static/` (gitignored, bundled into the wheel; the build hook refuses to build without it) and Flask serves it at `/`; the JSON API lives under `/api` (all endpoints below are relative to it). `nt2gui serve` (`nt2gui/cli.py`) runs it with waitress in a single multi-threaded process — open simulations, caches and the session are in-memory, so never use multiple worker processes, and guard shared mutable state with locks. It binds `127.0.0.1` by default and prints an SSH tunnel command; the intended setup is the server on a cluster next to the data and the browser on the user's machine. `nt2gui server` runs the API alone (`create_app(with_client=False)`) and `nt2gui client` the UI alone (`nt2gui/static_client.py`, no data dependencies); a separately served UI calls the API cross-origin, which is allowed only for `--allow-origin` origins (CORS allowlist in `app.py`, default the client's `http://localhost:8766`) because the API can write files on the server.
- The client uses relative URLs by default (`client/src/config.ts`, vite `base: "./"`) so it works behind any port or path prefix; `npm run dev` proxies `/api` to Flask. A different server URL can be set per browser (Settings, the offline screen, or a `?server=` link); it is stored in localStorage, not in the synced session. `npm run package` builds the client and then the wheel/sdist; CI (`.github/workflows/ci.yml`) tests, builds, and publishes to PyPI on `v*` tags.
- Ultimately, the backend will be paired with the `nt2py` package to provide a UI for visualization (https://github.com/entity-toolkit/nt2py)
- The frontend is a react-based vite app written in typescript which uses flex-layout for to display multiple panels with selectable plots.
- The UI state should be synchronized with the server which must keep track of it and potentially recover at initialization.
  - The server owns the session (`nt2gui/session/store.py`): it always has a valid state (defaults from `nt2gui/session/schema.py`), persists it to `$NT2GUI_STATE_FILE` (default `.nt2gui/session.json`) with atomic writes, and re-opens saved simulations on restart.
  - `GET /state` returns `{revision, state, simulations}`; `PUT /state` takes `{revision, state}` and returns 409 with the current snapshot when the revision is stale. Simulation commands return the same snapshot.
  - Saved sessions (`nt2gui/session/files.py`, which also holds the schema migrations) are the session without its revision: `{schemaVersion, state, simulations}`. `POST /session/save|load {path}` writes/reads files on the server machine (409 on overwrite unless `overwrite: true`); `GET /session/export` and `POST /session/import {session}` back the client-side download/upload. Loading replaces the whole session, re-opens its simulations (reporting failures in `warnings`), and bumps the revision.
  - The client never initializes the state: it renders only after `GET /state`, and all writes go through `client/src/state/StateSync.ts` (debounced, serialized, retried; server wins on conflict).
  - When changing the state shape, update `client/src/state/schema.ts` and `nt2gui/session/schema.py` together (bump `SCHEMA_VERSION` and add a migration for breaking changes).
- Plots are shaded on the server side, but the axes as well as the colorbars (if applicable) are reconstructed on the client-side using d3 elements.
  - The server returns only the image (`nt2gui/render.py:shade`, no matplotlib figures — pyplot isn't thread-safe), its extent in data units (outer cell/bin edges) and the color limits; `client/src/charts/ImageChart.tsx` draws both 2D plot types with matching d3 scales.

# Code layout
- Server (`nt2gui/`), one direction of dependencies: `api/` → `plots/` → `data/` + `render.py` → `sources/` + `session/`.
  - `app.py` wires the `Workspace` (`workspace.py`: session store + open simulations + lock, Flask-free), the `api/` blueprints (`state`, `simulations`, `fields`, `particles`; helpers in `api/common.py`) and the static client.
  - Errors: domain code raises `nt2gui/errors.py:UserError` (or `NotFound`/`Conflict`, or subclasses like `ExpressionError`, `QuantityError`) for bad input; one handler turns them into JSON errors with their status. Routes don't try/except; anything else is a bug and a 500. Validate request bodies with the pydantic models (`api.common.parse`).
  - `plots/<kind>.py` turns a validated config into a response; `data/` holds reusable pieces (`quantities.py`: resolving quantities, `snapshot_at`, `cut`; `particles.py`: particle datasets, scales, binning; `metadata.py`; `expressions.py`).
  - Tests share fixtures in `tests/conftest.py` and helpers (`put_state`, `load_demo`) in `tests/helpers.py`.
- Client (`client/src/`):
  - `api/` (one module per server area; `http.ts` has `requestJson`, URL helpers, `serverErrorMessage`; response types in `api/types.ts`), `state/` (`schema.ts`, pure `plotters.ts` reducers, `useServerSession.ts`, `UiContext.tsx` providing `useUi()` / `useUiActions()` — no prop drilling), `charts/` (d3 charts and scales), `components/common` + `components/layout`, `lib/` (pure helpers), `hooks/` (`useCachedResource` for load-once data, `useServerRender` for latest-request-wins renders).
  - Plot kinds live in `plots/<kind>/` (Plot component using `PlotFrame`, Figure, Controls, pure `config.ts` with tests) and are listed in `plots/registry.ts`. Adding a plot type: a new folder, its config in both schemas, and one registry entry (plus a `nt2gui/plots/` module and route if it needs new data).

# Data format on the backend
- Simulations are opened by `nt2gui/sources/__init__.py:open_simulation`: a path like `demo:run` gives synthetic data (`nt2gui/sources/demo.py`); anything else is an Entity output directory read with nt2py (`nt2gui/sources/nt2.py`, lazy dask-backed fields; particles loaded one step at a time into a thread-safe `sources/cache.py:StepCache`). Both implement `SimulationSource` (fields, species, timeline, particles(time), particle_time(time)). nt2py knows species only by index, so labels and masses come from Entity's `<name>.info`.
- `GET /simulations/<id>/summary` (`nt2gui/data/metadata.py`) describes a simulation's fields, particles (species, masses, counts) and spectra — axes, resolution, output times, quantities — for the left sidebar where simulations are loaded.
- Integration tests in `tests/test_nt2loader.py` run against real output at `$NT2GUI_TEST_DATA` (default `~/Codes/entity/temp/deposit/dep-esirkepov`) and skip when it's absent.
- The data will consist of two different types: fields (multi-D arrays with 1D/2D or 3D coordinates at different timesteps represented with an xarray dataset), and particles (pandas dataframe containing particle species index, coordinates, ids, velocities, and corresponding timesteps etc.).
- Particle plots (`nt2gui/data/particles.py`, `nt2gui/plots/particle_*.py`) are weighted histograms of one time step: 1D (`particleHistogramConfig`, several lines of different species sharing one binned x axis) and 2D phase space (`particlePhaseConfig`, shaded on the server). Quantities are the columns (`x`, `y`, `z`, `ux`, `uy`, `uz`, `w`), `gamma = sqrt(1 + u²)`, `energy = |u|` (massless species), or expressions. Axes bin uniformly in linear, log10, or `sign(A)|A|^p` space; the client uses the matching d3 scale (`scaleLog`, sign-preserving `scalePow`) so ticks show data values. An empty species list means all species.
- Fields have names and the user should be able to combine them (and, potentially, the coordinates) to create new variables.
  - Custom quantities are expression strings (e.g. `sqrt(Ex**2 + Ey**2)`) evaluated by `nt2gui/data/expressions.py`, an AST whitelist over fields, coordinates and numpy functions — never `eval`. Anywhere a field name is accepted (1D `quantities`, 2D `field`), an expression is too; each plot keeps its list in `expressions`, and `POST /simulations/<id>/quantities/check` validates one and returns its dims.

# Guidelines
- Use both react typescript and Python best-practices.
- Run `pip install -r requirements.txt` (or `pip install -e ".[dev]"`) to install python requirements and use `npm i` to install node requirements.
- use `npm run dev` to run both the server and the client concurrently.
- The state of UI must be fully reproducible and synchronized with the server.
- Run tests with `npm run test` (typecheck + vitest + pytest), in the most error-prone routines -- always add unit tests.
